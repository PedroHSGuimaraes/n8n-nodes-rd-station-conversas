# Project state

## Decisions

| ID | Decision | Rationale | Status | Date |
| --- | --- | --- | --- | --- |
| AD-001 | Pacote npm `n8n-nodes-rd-station-conversas`, versão 1.0.0, repositório GitHub `PedroHSGuimaraes/n8n-nodes-rd-station-conversas`; um serviço por pacote | O dono decidiu em 06/11/2026; a guideline de verificação do n8n pede um serviço por pacote e o Conversas é um produto separado do CRM e do Marketing | active | 2026-11-06 |
| AD-002 | Toolchain do `@n8n/node-cli` 0.55.5 (`n8n-node build`, `n8n-node lint`, `n8n.strict: true`), sem `dependencies` de runtime; testes com `node --test` sobre o `dist`; CI no PR (lint, test, build) e publicação por tag `v*` com provenance | O dono decidiu; é o padrão do template oficial e do pacote Vizard, e a verificação do n8n exige zero dependência de runtime | active | 2026-11-06 |
| AD-003 | Credencial `rdStationConversasApi`: token JWT em campo senha enviado como `Authorization: Bearer`, base URL fixa `https://api.tallos.com.br`, teste `GET /v2/employees`; mais um campo opcional de senha com a chave privada RSA em JWK, usada só no histórico | O Conversas não tem OAuth, client id nem refresh: o token é estático e gerado no painel. A chave só serve ao histórico, então é opcional | active | 2026-11-06 |
| AD-004 | Node de ação `rdStationConversas` em estilo programático (`execute`), `usableAsTool: true`, padrão Resource → Operation, Resource Locator com `From list` como padrão para todo ID que tenha listagem, Return All + Limit onde a rota pagina, `{ "deleted": true }` nas exclusões, rótulos em inglês Title Case, placeholders `e.g. ...`, telefone E.164 com dica no campo, erros no formato da UX guideline | O dono decidiu. Estilo programático escolhido pelo Jev (1,00 contra declarativo 0,00): o node decripta JWE, monta o corpo das exclusões em massa, normaliza telefone e pagina, o que `routing` não faz | active | 2026-11-06 |
| AD-005 | Contato nas rotas que pedem o `_id` usa Resource Locator com três modos: `From list`, `By Phone` e `By ID`. O modo `By Phone` resolve o telefone com `GET /v2/contacts/{cel_phone}/exists` | Jev 0,97 contra dois modos 0,03. Quem usa WhatsApp conhece o telefone, não o `_id` de 24 caracteres | active | 2026-11-06 |
| AD-006 | Sem node gatilho (trigger) | A documentação do Conversas não descreve webhook, evento nem payload; os webhooks documentados são do RD CRM e do Marketing | active | 2026-11-06 |
| AD-007 | As rotas deprecadas ficam fora: `POST /v2/contacts`, `POST /v2/contacts/whatsapp-business`, `PUT /v2/contacts/whatsapp-business`, `POST /v2/messages/{contact_id}/send-template-filled`, `POST /v2/messages/{contact_id}/send-template-filled-by-brokers` e `POST /api/v3/message/template/send` | O dono decidiu; a doc as marca como deprecadas e indica as rotas novas | active | 2026-11-06 |
| AD-008 | Operações em massa irreversíveis entram: apagar contatos por tag e por integração, e reiniciar o fluxo dos contatos com aviso na descrição. A opção `$all` (apagar todos os contatos) NUNCA é enviada nem exposta | O dono decidiu. Um clique errado apagaria a base inteira da empresa; sem a opção, o pior caso fica limitado a uma tag ou a uma integração | active | 2026-11-06 |
| AD-009 | O histórico de mensagens (`GET /v2/messages/history`, planos Pro e Advanced) entra. O node decripta o JWE compacto (RSA-OAEP-256 mais o `enc` do cabeçalho) com o módulo nativo `node:crypto`, sem dependência, usando a chave JWK da credencial. Sem a chave, a operação falha antes da chamada, com mensagem que diz onde gerar a chave | O dono decidiu. A doc usa `node-jose`, mas a regra de zero dependência de runtime proíbe pacote; `node:crypto` importa JWK e decripta RSA-OAEP e AES | active | 2026-11-06 |
| AD-010 | O plano cobre as 42 rotas não deprecadas do catálogo; o que ficar de fora vai para `Out of scope` com motivo, e cada lacuna NÃO CONFIRMADA vira linha de `Assumptions` com default e `Confirmed? n` | O dono decidiu. O catálogo tem 47 rotas e 5 estão deprecadas | active | 2026-11-06 |
| AD-011 | Código comentado em PT-BR, linha a linha, com o porquê; toda chamada HTTP com `timeout` explícito; README em PT-BR no formato do pacote CRM; `CHANGELOG.md` | Regras da casa do dono | active | 2026-11-06 |
| AD-012 | Um único plano (`rd-station-conversas-v1`) com fatias por resultado observável, não um plano por recurso | Jev 0,89 contra um plano por recurso 0,11. As portas de mão única (nomes persistidos, formato de saída, criptografia) se revisam juntas | active | 2026-11-06 |
| AD-013 | A operação `flow.resetAllContactsFlow` exige o campo `Confirm Restart` (`confirmRestart`, booleano, padrão falso); sem ele a operação falha antes de qualquer requisição | O dono decidiu no meio da construção (06/11/2026). A rota não documenta escopo e pode reiniciar o fluxo de todos os contatos | active | 2026-11-06 |
| AD-014 | A tag `v1.0.0` só sai depois que o dono testar com conta real (formato do JWE do histórico e envio de mensagem). Entrega: versão 1.0.0, CHANGELOG, workflows prontos, sem tag; o README explica `npm run dev` e a geração da chave JWK | O dono decidiu (06/11/2026). Dois contratos (`enc` do JWE e corpo de envio) estão NÃO CONFIRMADOS na doc | active | 2026-11-06 |
| AD-015 | O texto aberto do JWE do histórico é lido como UTF-8 estrito e, se os bytes não forem UTF-8 válido, como latin1 | A revisão the-judge reproduziu com node-jose 2.2.0 que uma string passada ao `update` (exemplo oficial) sai em latin1. A codificação real da API fica para o teste com conta real (C91) | active | 2026-11-06 |
| AD-016 | A publicação usa `npx -y npm@12.2.2 stage publish --provenance --access public` com `RELEASE_MODE=true` no lugar de `npm run release`: a versão fica em espera e o dono a aprova com 2FA na aba Staged Packages do npmjs.com; o `publish.yml` ganha `workflow_dispatch` | O dono manteve o token granular do npm "Read and write (stage only)"; com ele `npm publish` falha com `E_STAGE_REQUIRED`. `npm stage` só existe no npm 12 e o Node LTS do runner traz o npm 11. O `prepublishOnly` (`n8n-node prerelease`) exige `RELEASE_MODE`. Decisão do dono, 06/11/2026 | active | 2026-11-06 |
